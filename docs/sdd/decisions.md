# Решения SDD

## Принятые решения

### D-001 OpenAPI кодогенерация

- Использовать Hey API.
- Генерировать только SDK и типы.
- TanStack Query держать рукописным.

### D-002 API-границы

- Держать сгенерированные артефакты изолированными в выделенной папке generated.
- Не импортировать сгенерированные артефакты напрямую из `pages`, `widgets`, `features` или `entities`.
- Все обращения к API — через `shared/api`.

### D-003 Стратегия роутера

- Использовать TanStack Router в code-based режиме.
- Сопрягаемые с маршрутами компоненты страниц должны соответствовать правилу именования `*.component.tsx`.

### D-004 Стратегия UI-state

- Использовать Zustand только для точечного клиентского UI-state.
- Серверное состояние держать в TanStack Query.

### D-005 Стратегия стилизации

- Использовать Tailwind CSS.
- Использовать `shadcn/ui` как foundation для UI-компонентов.

### D-006 Персистентность фильтров

- Источник истины для фильтров списка — URL search params.
- Валидировать search params через Zod с безопасными fallback-значениями.

### D-007 UX-структура ставок

- Реализовать историю ставок как вложенный маршрут/вкладку внутри маршрута аукциона.

### D-008 Минимум тестов (TDD per-task)

- Logic-тесты не выделены в отдельную финальную задачу. Каждую порождающую логику задачу закрываем TDD-циклом: тесты пишутся вперёд и должны загораться красным по правильной причине, затем пишется минимальная реализация, затем рефакторинг.
- Минимум покрывает:
  - двусторонний URL-контракт фильтров — parse + serialize + defaults-detection (в `SDD-015`),
  - логику request builder (в `SDD-016`),
  - display-лейблы enum'ов аукциона (в `SDD-018`, живут в `entities/auction/lib`),
  - view-model-мапперы ставок (в `SDD-023`),
  - схему валидации ставки (в `SDD-024`).
- Раннер — Vitest. Он ставится в `SDD-015` (первая задача, порождающая logic-тесты), чтобы последующие TDD-задачи просто переиспользовали готовый `pnpm test`. Выбор обоснован: Vite + tsconfig path-алиасы работают из коробки, нативный ESM, минимальный конфиг.
- Файл задачи `SDD-028 Logic Tests` удалён; его ответственность распределена по задачам-источникам. Номер `028` больше не используется (номера SDD — это стабильные идентификаторы, перенумерация не делается).
- UI/Renderer-тесты остаются вне scope logic-минимума и при необходимости добавляются отдельно.

### D-009 Стратегия mock runtime

- Использовать единое in-memory MSW runtime-хранилище.
- Обработчики list, detail и bets читают из одного рантайм-состояния.
- Мутация ставки обновляет то же состояние.

### D-010 Количество участников

- Поскольку endpoint ставок не отдаёт выделенное поле количества участников, выводить участников из доступных записей ставок.
- Задокументировать это явно в заметках по реализации и в README-заметках о верификации при необходимости.

### D-011 Идентичность Auction UUID

- OpenAPI-спецификация маршрутизирует аукционы по `auctionUuid: format: uuid` в path-параметрах (`/auctions/{auctionUuid}`, bets, set-bet), но не экспонирует поле `auction_uuid` ни в одном DTO ответа. Mock-слой закрывает этот контрактный разрыв так, как сделал бы реальный бэкенд: MSW инжектит `main.auction_uuid` в ответы `AuctionListItem`, чтобы клиент мог перейти из списка в детальную карточку без угадываний.
- Обоснование: явное расширение лучше неявной интерпретации. Ранее мы рассматривали трактовку `auctionUuid` как семантически эквивалентной `main.order_uid` (единственный UUID в DTO), но это прятало бы логику роутинга за записью в `decisions.md`, которую ревьюер должен найти. Поле расширения видно в сетевых ответах и самодокументируемо. Также оно forward-compatible: если будущая ревизия схемы добавит `auction_uuid` в DTO, поменяется только mock-слой — клиентский код уже читает поле по имени.
- `auction_uuid` намеренно отличен от `order_uid`. Домен грузовых аукционов трактует аукцион как торговую процедуру, наслоённую поверх заказа; смешение их идентификаторов потеряло бы разделение, которое поддерживает реальная система.
- Реализация: `MockAuctionListItemMain` (в `src/shared/api/mocks/auctions.ts`) расширяет сгенерированный `AuctionListItemMain` обязательным полем `auction_uuid`. `SeedAuction.uuid === list.main.auction_uuid`, при этом `SeedAuction.list.main.order_uid` остаётся независимым под `seedOrderUids`. MSW-обработчики (SDD-011+) резолвят path-параметры по совпадению с `main.auction_uuid`; клиентские ссылки строятся как `params={{ auctionUuid: item.main.auction_uuid }}`.
- Объём отклонения: это mock-only расширение сгенерированного DTO. Оно НЕ ДОЛЖНО протекать в production-типы `shared/api` или в `entities` / `features` / `widgets` / `pages`. Когда клиенту нужно прочитать `auction_uuid`, он должен делать это через типизированный view-model-маппер, потребляющий `MockAuctionListItem` только внутри MSW-setup и тестов.

### D-012 Двусторонний URL-контракт фильтров

- SDD-015 владеет **обоими** направлениями transform'а «URL search params ↔ типизированный объект фильтров»: parse (Zod-схема) И serialize (typed → `URLSearchParams`), а также defaults-хелперами (`isDefaultFilters`, `countActiveFilters`).
- Обоснование: parse и serialize — обратные операции с общим инвариантом round-trip. Разделение их по разным задачам нарушило бы этот инвариант и заставило бы синхронизировать два модуля при каждом изменении набора фильтров. Двусторонний контракт в одном модуле делает round-trip-test'ы естественной частью TDD-цикла.
- SDD-018 (UI фильтров) НЕ владеет фильтр-логикой. Компоненты только подписываются на типизированный объект из SDD-015 и при изменении вызывают serialize + navigate. Любой transform внутри `*.component.tsx` — сигнал, что его надо перенести в SDD-015 (URL-контракт) или в `entities/auction/lib` (доменные мапперы enum'ов).
- Default-значения намеренно НЕ сериализуются в URL, чтобы ссылка оставалась читаемой и устойчивой к изменению дефолтов.

### D-014 Weight/Volume фильтры за рамками минимума

- `weight_from`/`weight_to`/`volume_from`/`volume_to` присутствуют в `AuctionListRequest` OpenAPI-схемы, но НЕ входят в минимальный набор фильтров из `project_requirements.md` (строки 62-71).
- Решение: URL-контракт SDD-015 их НЕ покрывает; request builder (SDD-016) их НЕ маппит; UI-фильтры (SDD-018) их НЕ отображают. При появлении продуктовой необходимости — добавить осознанным расширением в SDD-015 → SDD-016 → SDD-018 одновременно, чтобы round-trip-инвариант не нарушался.
- Обоснование: соответствие минимальному набору требований важнее покрытия всех полей API; расширение списка фильтров должно быть явным и синхронным по трём задачам, а не точечным.

### D-013 Display-лейблы для enum'ов

- Человекочитаемые русские лейблы для доменных enum'ов (`AuctionType`, `TradingStatus`, body-type строки и т. п.) живут в `src/entities/auction/lib/` как `Record<Enum, string>`-таблицы и экспонируются через Public API слайса (`describeAuctionType`, `describeTradingStatus`, ...).
- Обоснование: лейблы — это доменное отображение, а не UI-декорация; их первый потребитель — SDD-018 (фильтры), но также SDD-019 (карточка) и позже ставка/детали. Централизация в entity-слое гарантирует: разные UI используют одинаковые термины, а опечатки ловятся одним тестом на маппер (TDD, в `pnpm test`).
- Не использовать отдельный `shared/i18n`-слой, пока нет мультиязычности или переиспользования вне auction-домена — это преждевременная абстракция.

## Ограничения

- Точность OpenAPI-контракта важнее удобства.
- DTO-ограничения должны двигать UI.
- Если формулировка требований и схема расходятся, предпочесть схему и задокументировать решение.
