# Решения SDD

## Принятые решения

### D-001 OpenAPI кодогенерация

- Использовать Hey API.
- Генерировать только SDK и типы.
- TanStack Query держать рукописным.

### D-002 API-границы

- Держать сгенерированные артефакты изолированными в выделенной папке generated.
- Не импортировать сгенерированные артефакты напрямую из `pages`, `widgets`, `features` или `entities`.
- Все обращения к API — через `shared/api`.

### D-003 Стратегия роутера

- Использовать TanStack Router в code-based режиме.
- Сопрягаемые с маршрутами компоненты страниц должны соответствовать правилу именования `*.component.tsx`.

### D-004 Стратегия UI-state

- Локальный state одного компонента — через React `useState`. Не тянуть Zustand там, где владелец один (например, open/close фильтров в `AuctionFilters`).
- Zustand — только для UI-state, который действительно разделяется между дальними компонентами или переживает unmount (например, multi-step wizard, live filter draft на странице списка). Если такие сценарии не появились, Zustand не вводится.
- Серверное состояние держать в TanStack Query.
- URL-параметры — отдельный источник истины для фильтров/пагинации; не дублировать их в Zustand или `useState`.

### D-005 Стратегия стилизации

- Использовать Tailwind CSS.
- Использовать `shadcn/ui` как foundation для UI-компонентов.

### D-006 Персистентность фильтров

- Источник истины для фильтров списка — URL search params.
- Валидировать search params через Zod с безопасными fallback-значениями.

### D-007 UX-структура ставок

- Реализовать историю ставок как вложенный маршрут/вкладку внутри маршрута аукциона.

### D-008 Минимум тестов (TDD per-task)

- Logic-тесты не выделены в отдельную финальную задачу. Каждую порождающую логику задачу закрываем TDD-циклом: тесты пишутся вперёд и должны загораться красным по правильной причине, затем пишется минимальная реализация, затем рефакторинг.
- Минимум покрывает:
  - двусторонний URL-контракт фильтров — parse + serialize + defaults-detection (в `SDD-015`),
  - логику request builder (в `SDD-016`),
  - display-лейблы enum'ов аукциона (в `SDD-018`, живут в `entities/auction/lib`),
  - view-model-мапперы ставок (в `SDD-024`),
  - схему валидации ставки (в `SDD-025`).
- Раннер — Vitest. Он ставится в `SDD-015` (первая задача, порождающая logic-тесты), чтобы последующие TDD-задачи просто переиспользовали готовый `pnpm test`. Выбор обоснован: Vite + tsconfig path-алиасы работают из коробки, нативный ESM, минимальный конфиг.
- Logic-тесты не выделены в отдельную задачу: TDD встроен в задачи-источники (`SDD-015`/`SDD-016`/`SDD-024`/`SDD-025`). Ранее планировалась выделенная задача «Logic Tests», от неё отказались в пользу per-task TDD.
- UI/Renderer-тесты остаются вне scope logic-минимума и при необходимости добавляются отдельно.

### D-008a Политика перенумерации SDD-задач

- SDD-задачи нумеруются строго последовательно. При вставке новой задачи между существующими делается равномерный сдвиг всех последующих номеров на +1 (включая переименование файлов через `git mv` для сохранения истории).
- Все cross-references — внутри task-файлов, в `decisions.md`, в `README.md` и в `AI_USAGE.md` — обновляются одновременно со сдвигом. Замены делаются через regex по цепочкам вида `SDD-0XX/YY/ZZ`, чтобы shorthand-запись (без префикса `SDD-` у каждого элемента) тоже сдвигалась корректно.
- Исторические ссылки на удалённые задачи (например, «Logic Tests») переписываются явно: memorial-формулировки вида «номер N больше не используется» удаляются, чтобы не конфликтовать с новым жителем слота.
- Обоснование: номера SDD — это одновременно archive-идентификаторы и навигационные якоря. Раньше приоритет отдавался стабильности (D-008 запрещал перенумерацию); после вставки UI-redesign-задачи (SDD-019) приоритет смещён в пользу contiguous-нумерации, потому что разрывы и устаревшие memorial-записи затрудняют чтение индекса задач новыми ревьюерами.

### D-009 Стратегия mock runtime

- Использовать единое in-memory MSW runtime-хранилище.
- Обработчики list, detail и bets читают из одного рантайм-состояния.
- Мутация ставки обновляет то же состояние.

### D-010 Количество участников

- Поскольку endpoint ставок не отдаёт выделенное поле количества участников, выводить участников из доступных записей ставок.
- Задокументировать это явно в заметках по реализации и в README-заметках о верификации при необходимости.

### D-011 Идентичность Auction UUID

- OpenAPI-спецификация маршрутизирует аукционы по `auctionUuid: format: uuid` в path-параметрах (`/auctions/{auctionUuid}`, bets, set-bet), но list DTO не отдаёт этот идентификатор ни в одном поле ответа.
- `order_uid` не приравнивается к `auctionUuid` на transport-уровне. Это другой доменный идентификатор, и подмена одного другим в path была бы скрытым contract drift.
- Реализация после SDD-032: внешний route contract приложения использует `auctionRef`, который в текущем mock-backed приложении равен `main.order_uid`. Adapter-layer (`shared/api`) резолвит `auctionRef -> auctionUuid` через mock runtime lookup и только затем вызывает OpenAPI endpoints.
- Выигрыш такого подхода: production DTO больше не расширяется несуществующим полем, UI не читает invented field, а контрактный разрыв остаётся явным и локализованным в одном resolver boundary.
- Ограничение подхода: это по-прежнему mock-era workaround. Для реального backend корректный list -> detail flow требует либо явного `auctionUuid` в list DTO, либо отдельного контрактного endpoint/lookup механизма.

### D-012 Двусторонний URL-контракт фильтров

- SDD-015 владеет **обоими** направлениями transform'а «URL search params ↔ типизированный объект фильтров»: parse (Zod-схема) И serialize (typed → `URLSearchParams`), а также defaults-хелперами (`isDefaultFilters`, `countActiveFilters`).
- Обоснование: parse и serialize — обратные операции с общим инвариантом round-trip. Разделение их по разным задачам нарушило бы этот инвариант и заставило бы синхронизировать два модуля при каждом изменении набора фильтров. Двусторонний контракт в одном модуле делает round-trip-test'ы естественной частью TDD-цикла.
- SDD-018 (UI фильтров) НЕ владеет фильтр-логикой. Компоненты только подписываются на типизированный объект из SDD-015 и при изменении вызывают serialize + navigate. Любой transform внутри `*.component.tsx` — сигнал, что его надо перенести в SDD-015 (URL-контракт) или в `entities/auction/lib` (доменные мапперы enum'ов).
- Default-значения намеренно НЕ сериализуются в URL, чтобы ссылка оставалась читаемой и устойчивой к изменению дефолтов.

### D-014 Weight/Volume фильтры за рамками минимума

- `weight_from`/`weight_to`/`volume_from`/`volume_to` присутствуют в `AuctionListRequest` OpenAPI-схемы, но НЕ входят в минимальный набор фильтров из `project_requirements.md` (строки 62-71).
- Решение: URL-контракт SDD-015 их НЕ покрывает; request builder (SDD-016) их НЕ маппит; UI-фильтры (SDD-018) их НЕ отображают. При появлении продуктовой необходимости — добавить осознанным расширением в SDD-015 → SDD-016 → SDD-018 одновременно, чтобы round-trip-инвариант не нарушался.
- Обоснование: соответствие минимальному набору требований важнее покрытия всех полей API; расширение списка фильтров должно быть явным и синхронным по трём задачам, а не точечным.

### D-013 Display-лейблы для enum'ов

- Человекочитаемые русские лейблы для доменных enum'ов (`AuctionType`, `TradingStatus`, body-type строки и т. п.) живут в `src/entities/auction/lib/` как `Record<Enum, string>`-таблицы и экспонируются через Public API слайса (`describeAuctionType`, `describeTradingStatus`, ...).
- Обоснование: лейблы — это доменное отображение, а не UI-декорация; их первый потребитель — SDD-018 (фильтры), но также SDD-019 (UI-redesign) и SDD-020 (карточка), позже ставка/детали. Централизация в entity-слое гарантирует: разные UI используют одинаковые термины, а опечатки ловятся одним тестом на маппер (TDD, в `pnpm test`).
- Не использовать отдельный `shared/i18n`-слой, пока нет мультиязычности или переиспользования вне auction-домена — это преждевременная абстракция.

### D-015 Сквозная тема приложения и название «ГрузоТорг»

- Тема приложения — три состояния: `system | light | dark`. По умолчанию берётся системная предпочтение (`prefers-color-scheme`); явный выбор пользователя персистится в `localStorage` под ключом `theme`. Применяется через класс `.dark` на `document.documentElement` — токены и `@custom-variant dark` заведены в SDD-004, отдельных цветовых схем не вводится.
- Тема владеет слайсом `src/shared/theme/` (хук + lib):(matchMedia-подписка, чтение/запись `localStorage`, применение класса). Переключатель живёт в `src/features/theme-toggle/`, шапка — в `src/widgets/header/`. Любой другой код не должен читать `localStorage.theme` или мутировать `documentElement.classList` напрямую — только через публичный API слайса.
- Для предотвращения FOUC в `index.html` ставится синхронный инлайн-скрипт в `<head>`, который до отрисовки React добавляет класс `.dark` по сохранённому выбору или системной предпочтении. Это единственное место вне React-дерева, легально читающее `localStorage.theme`.
- Продуктовое название приложения — «ГрузоТорг». Зафиксировано как единый источник: `<title>` в `index.html`, текстовый знак в шапке, потенциальная будущая мета-разметка. Лого шапки переиспользует `public/favicon.svg` (дублирование SVG-контента в компоненте запрещено).
- Обоснование: тема — это сквозная инфраструктура с инвариантом «класс на `<html>` === выбор пользователя === отображаемая палитра». Централизация в одном слайсе делает инвариант проверяемым и предсказуемым; вынесение FOUC-скрипта в `index.html` — необходимое исключение, без которого первый пэйнт расходится с React-состоянием.

## Ограничения

- Точность OpenAPI-контракта важнее удобства.
- DTO-ограничения должны двигать UI.
- Если формулировка требований и схема расходятся, предпочесть схему и задокументировать решение.
