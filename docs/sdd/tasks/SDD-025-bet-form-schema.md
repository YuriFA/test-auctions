# SDD-025 Bet Form Schema

## Статус

Не начато.

## Цель

Определить модель валидации установки ставки.

## Охват

- Построить React Hook Form и Zod-схему валидации.
- Использовать ограничения detail DTO для `min`, `max`, `step` и подсказок по доступной цене.
- TDD: тесты на схему валидации ставки пишутся ПЕРВЫМИ, до подключения формы к UI.

## Зависимости

- `SDD-012`
- vitest-раннер из `SDD-015`

## TDD-порядок

1. Написать красные тесты на чистую функцию валидации ставки (`validateBetPrice(input, constraints)` или `betFormSchema(constraints).safeParse(input)`):
   - цена обязательна и больше нуля;
   - при наличии `min`/`max` из detail DTO — выход за границы даёт осмысленную ошибку с правильным путём (`path: ['price']`);
   - `step` (если есть) проверяется: цена, не кратная шагу от базовой, отклоняется;
   - null/missing ограничительные поля (форма не предполагает их наличия) → валидация проходит с одним только `> 0` правилом;
   - доступная цена (`available`) используется только как подсказка, а не как жёсткое ограничение, если это явно не задано в контракте;
   - нечисловой ввод (`"abc"`, `""`) → структурная ошибка, а не исключение.
2. Запустить тесты, убедиться, что они красные по правильной причине.
3. Реализовать Zod-схему как фабрику от constraints, чтобы покрыть тесты.
4. Подключить схему к React Hook Form в SDD-027 (wiring `useForm` + `zodResolver`, рендер `errors`, состояние `isSubmitting` — ответственность SDD-027, не этой задачи).

## Критерии приёмки

- Цена обязательна и больше нуля.
- Условные ограничения из detail DTO применяются, когда они есть.
- Поведение валидации покрыто тестами в `pnpm test` (включая edge-case'ы выше).

## Заметки и риски

- Форма не должна предполагать, что все торговые ограничительные поля присутствуют.
- Схема — фабрика от detail-констрейнтов, не глобальная константа: тесты создают синтетические constraints и проверяют behavior.
- Тесты на схему не требуют рендеринга формы: Zod-объект можно тестировать напрямую через `.safeParse()`.
