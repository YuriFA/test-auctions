## Какие решения принял кандидат

- Использовать Hey API для сгенерированных SDK и типов.
- Держать TanStack Query рукописным, а не сгенерированным.
- Использовать code-based TanStack Router.
- Использовать Zustand для точечного клиентского UI-state.
- Использовать URL search params для фильтров.
- Использовать Tailwind CSS вместе с `shadcn/ui`.
- Сделать историю ставок вложенным маршрутом/вкладкой.
- Держать `AGENTS.md` только как полиси/правила.
- Требовать суффикс `*.component.tsx` для всех React-компонентов.
- Держать сгенерированный OpenAPI-слой изолированным за `shared/api`.
- Использовать `steiger` для поддержки границ Feature-Sliced Design.
- Смапить алиасы `components.json` shadcn на FSD-слои (`@shared/ui`, `@shared/lib`) вместо дефолтных `@/components` и `@/lib`.
- Разделять каждый shadcn UI-примитив на `*.component.tsx` и `*.styles.ts`, чтобы пройти `react(only-export-components)`.
- Трактовать code-based маршруты TanStack Router как файлы `.route.tsx`, а компоненты страниц — как `*.component.tsx` в `src/pages/<slice>/ui/`, доступные через Public API слайса `index.ts`.
- Положить синглтон QueryClient в `src/app/lib/`, а не в `app/providers` или `app/store`, потому что `fsd/segments-by-purpose` у steiger помечает оба как content-named.
- Пинить входы Hey API к относительным путям, начинающимся с `./`, чтобы v0.99 не разбирал их как cloud-shorthand «organization/project».
- Держать сгенерированные OpenAPI-артефакты read-only и исключёнными из линта; доставать их только через рукописный адаптер `shared/api`.
- Оборачивать вызовы сгенерированного SDK в функции-адаптеры `shared/api`, которые бросают унифицированные `ApiError` / `ApiValidationError`, вместо того чтобы протекать формой `RequestResult` Hey API в вызывающий код.
- Держать query-ключи в одной иерархической фабрике (`auctionKeys`) под `entities/auction`, чтобы list, detail и bets делили префиксы и мутация ставки могла инвалидировать все зависимые запросы разом.
- Разместить mock-датасет в `src/shared/api/mocks/` (подпапка production-сегмента `shared/api`, а не новый top-level-сегмент) и намеренно не реэкспортировать его из `src/shared/api/index.ts`, чтобы pages/widgets/features/entities не могли импортировать mock-данные и только MSW bootstrap, обработчики и тесты доставали их через `@shared/api/mocks`.
- Связать list + detail + bets в один `SeedAuction` на UUID, чтобы runtime-хранилище (SDD-010) и обработчики (SDD-011+) потребляли единый источник истины, а не сшивали три параллельных массива.
- Разместить runtime-хранилище в `src/shared/api/mocks/runtime/store.ts` (подпапка mock-датасета, а не новый top-level-сегмент) и реэкспортировать только типизированные операции через `src/shared/api/mocks/index.ts`. Рантайм владеет одним мутабельным `state.auctions`, инициализированным из `structuredClone(seedAuctions)`, поэтому обработчики всегда читают один источник, а `resetMockRuntime()` достаточен для восстановления детерминированного состояния между тестами.
- Сделать `writeBet` возвращающим discriminated union `PlaceBetResult` (`{ ok: true; bet } | { ok: false; status: 404 | 422; problem }`) вместо бросания исключения. Хранилище отвечает только за данные; HTTP-семантика остаётся за MSW-обработчиком (SDD-014). Возврат problem-объекта позволяет обработчику перевести его напрямую в `Response` без повторной валидации.
- Трактовать направление аукциона (`Down` — младшая выигрывает, `Up` — старшая) как единственный сигнал для ранжирования ставок и перевычисления `available`. `Request`, `FixPrice` и `Unknown` падают на «младшая выигрывает»; сид покрывает и `Down`, и `Up`, поэтому обе ветки остаются прокачаны.
- Автоматически отвергать предыдущую активную ставку пользователя при установке новой (как в существующем сиде `stoppedRejected`: `is_rejected = true`, `place = null`, `cancel_reason = "Перебито новой ставкой"`) вместо хранения нескольких параллельных активных ставок на пользователя. В сиде видна история из нескольких ставок с сохранёнными местами, потому что они предшествуют самой свежей ставке пользователя; когда приходит новая — предыдущая уходит в сторону.
- Держать MSW-handler для `POST /auctions/list` тонким: вся filter-/sort-/pagination-логика остаётся в `readAuctionList` runtime-store (SDD-010), handler владеет только HTTP-конвертом (parse JSON body → `AuctionListRequest`, вызвать store, обернуть `AuctionListResponseBase` в `HttpResponse.json`, отдать 422 `ValidationProblem` на некорректном JSON). Дублировать filter-логику в handler было бы ошибкой — она уже протестирована в SDD-010 и держит единый источник истины для всех будущих обработчиков.
- Использовать path-паттерн с leading-wildcard (`*/api/v1/auctions/list`) для MSW-handler'ов, чтобы один и тот же handler работал и в browser-worker (где SDK постит против текущего host), и в Node `setupServer` (где у `fetch` синтетический `http://localhost` origin). Относительный путь сматчился только в браузере; wildcard решает обе среды одинаково и не ослабляет семантику.
- Изолировать `msw/browser` в `src/shared/api/mocks/browser.ts` и НЕ реэкспортировать `setupWorker` из `mocks/index.ts`. Любой потребитель mock-слоя, импортирующий из `mocks/index.ts`, не должен тащить side-effectful `msw/browser` в свой бандл; `main.tsx` загружает browser-worker динамическим `import("@shared/api/mocks/browser")` только в `import.meta.env.DEV`, поэтому production-сборка вырезает worker tree-shaking'ом Vite. Массив handlers (`mockHandlers`) при этом безопасно реэкспортируется — это чистые данные.
- Запускать MSW worker с `await` перед `createRoot` в `main.tsx`, чтобы гарантировать, что ни один fetch приложения не уходит до готовности воркера. Стоимость — microtask на старте; выгода — детерминированный mock-слой без race-condition между `worker.start()` и первым API-запросом TanStack Query.
- Использовать `tsx` (не `--experimental-strip-types`) для запуска ad-hoc Node-smoke на TypeScript-модулях проекта. Native strip-types требует явных `.ts`-расширений во всех транзитивных импортах, а сгенерированный OpenAPI-слой использует extensionless-импорты — каскадное переименование было бы недопустимым вмешательством в `src/shared/api/generated/**`. `tsx` решает задачу одной devDep и не требует никаких изменений в существующих импортах.

## Какие AI-предложения были отклонены

- Не читать `auctionUuid` как семантически эквивалент `main.order_uid`. OpenAPI-спецификация маршрутизирует аукционы по `auctionUuid: format: uuid` в path-параметрах, но не экспонирует такого поля в DTO; `main.order_uid` — единственный UUID-образный идентификатор в list и detail. Приравнять их было бы проще, но цена слишком высока: логика роутинга спряталась бы за записью в `decisions.md`, разделение auction-vs-order схлопнулось бы, а ссылки в клиенте читались бы как `item.main.order_uid`, когда в URL стоит `auctionUuid`. Отклонено в пользу mock-only расширения `main.auction_uuid` (D-011): поле видно в ответах, forward-compatible и сохраняет две идентичности независимыми.
- Не генерировать React Query-хуки из OpenAPI-тулинга.
- Не экспортировать сгенерированные OpenAPI-артефакты напрямую в feature- и entity-слои.
- Не использовать localStorage как основной источник истины для фильтров.
- Не прятать поток ставок вне иерархии маршрута аукциона.
- Не прыгать сразу в реализацию фич до декомпозиции и архитектурных ограничений.

## Что проверялось особенно внимательно

- OpenAPI-поля с `format: uuid`. Hey API эммитит их как обычный `string`, поэтому typecheck один не поймёт UUID-образные значения. `order_uid` (на аукцион, одинаков в list и detail) теперь настоящий UUID; path-параметры `auctionUuid` и UUID сид-аукционов также используют каноническую форму `xxxxxxxx-xxxx-4xxx-8xxx-xxxxxxxxxxxx`. `chat_id` и `Contact.uid` типизированы как `string` без `format: uuid`, поэтому сохраняют короткие строковые значения.
- Контракто-чувствительные DTO-поля, особенно `nullable`.
- Различия enum-ов между list и detail.
- Валидация и обработка ошибок для `422`.
- DTO-driven UI-ограничения: скрытые контакты, скрытые цены, скрытая история ставок.
- Требования к консистентности mock-состояния после мутации ставки.
- Действительно ли находящиеся в работе файлы соответствуют заявленному SDD-прогрессу, а не только задуманному плану.
- URL-матчинг MSW-handler'а: относительный путь `/api/v1/auctions/list` сматчился в браузере, но не в Node `setupServer`, где у native fetch синтетический `http://localhost` origin — пришлось использовать leading-wildcard `*/api/v1/auctions/list`. Та же семантика работает и в браузере.
- Пагинация за пределами диапазона: `page > last_page` исторически возвращала `meta.from > total` (баг SDD-010). SDD-011 добавил в `buildMeta` параметр `pagedCount`, и пустая страница теперь даёт `from = 0, to = 0`, как Laravel-пагинатор и контракт `AuctionListMeta` (integer, не nullable).
- Что `await worker.start()` в `main.tsx` действительно происходит до `createRoot`, иначе первый API-запрос TanStack Query может уйти мимо воркера. Vite-древесный шейк `import.meta.env.PROD` гарантирует, что динамический `import("@shared/api/mocks/browser")` и весь `msw/browser` не попадают в production-сборку.

## Какие риски остаются

- Текущий код всё ещё близок к шаблонному бутстрапу и пока не отражает требуемой архитектуры приложения и экранов.
- Бутстрап уже заменяет Vite-демо и задаёт начальную структуру приложения, но бизнес-флоу пока отсутствуют.
- Часть продуктовых ожиданий шире, чем точные формы ответов в OpenAPI, поэтому некоторые значения UI, возможно, придётся выводить из доступных данных.
- Схема детальная и содержит много nullable-полей, что повышает риск случайных UI-допущений при реализации.
- Консистентность MSW между list, detail и bets может регрессировать, если обновления состояния реализовать в нескольких местах вместо одного runtime-хранилища. Именно контракт единого хранилища, введённый в SDD-010, защищает следующие задачи: обработчики (SDD-011 — SDD-014) должны вызывать `writeBet` и хелперы чтения, а не патчить DTO напрямую.
- В текущем бутстрапе пока нет интеграции React Hook Form, Zod или MSW. TanStack Router и TanStack Query подключены в `SDD-005`; Tailwind CSS и `shadcn/ui` — в `SDD-004`; Hey API SDK — в `SDD-006`; адаптер `shared/api` — в `SDD-007`; стратегия query-ключей — в `SDD-008`; mock-датасет — в `SDD-009`; in-memory MSW runtime-хранилище — в `SDD-010`; MSW-обработчик `POST /auctions/list` и browser-worker — в `SDD-011` (обработчики detail/bets/set-bet добавятся в SDD-012 — SDD-014, клиентские query появятся в SDD-017+). React Hook Form и Zod придут вместе с UI-формой ставки (SDD-024+).
- shadcn-компоненты по умолчанию шипят с двумя экспортами; каждый `shadcn add` требует ручного разделения на `*.component.tsx` и `*.styles.ts`, чтобы пройти линтер проекта.
- Playwright-smoke в `scripts/route-smoke.mjs` предполагает запущенный dev-сервер; он пока не подключён к CI-скрипту.
- Адаптер `shared/api` проверен только typecheck и build, рантайм-теста ещё нет; поведение покроют MSW-обработчики (SDD-010+) и logic-тесты (SDD-028).
- Query-ключи и план инвалидации ставки определены, но пока не потребляются; у слайса `entities/auction` нет входящих ссылок до SDD-017, где подключится первый list-запрос.
- Сгенерированный SDK экспортирует ~50 сырых OpenAPI-типов и 4 SDK-функции, которые downstream-код не должен импортировать напрямую; адаптер `shared/api` — граница, за которой app-коду доступны только нужные DTO и операции.
- Mock-датасет проверен typecheck, oxlint, steiger FSD-проверкой и production-build. MSW runtime-хранилище (SDD-010) потребляет его при загрузке модуля через `structuredClone`, а разовый Node-smoke проверил чтение, побочные эффекты мутации ставки на состояние, failure-ветки 404/422 и `resetMockRuntime()`. MSW-обработчик `POST /auctions/list` (SDD-011) проверён скриптом `scripts/msw-list-smoke.mjs` через `setupServer` из `msw/node` и native fetch (7 сценариев, 32 assertion: default body, pagination, пустая страница за диапазоном, фильтр `auc_type`, текстовый `cargo_num`, malformed JSON → 422, flip `is_oldest`), а также скриптом `scripts/msw-browser-smoke.mjs` через Playwright против живого dev-сервера (воркер регистрируется, fetch из page-context возвращает mock-данные). Smoke-скрипты закоммичены в `scripts/`, но не подключены к `pnpm check`; запускаются по требованию через `npx tsx scripts/msw-list-smoke.mjs` и `node scripts/msw-browser-smoke.mjs` (browser-smoke требует запущенного dev-сервера). Формальные logic-тесты появятся в SDD-028, когда добавится раннер.
- OpenAPI-спецификация маршрутизирует аукционы по `auctionUuid: format: uuid` в путях, но не экспонирует поле `auction_uuid` ни в одном DTO. Согласно `docs/sdd/decisions.md` D-011, мы закрываем этот контрактный разрыв в mock-слое так, как сделал бы реальный бэкенд: MSW инжектит `main.auction_uuid` в ответы `AuctionListItem` через mock-only тип `MockAuctionListItemMain`. `auction_uuid` намеренно отличен от `order_uid` (UUID лежащего в основе заказа), чтобы сохранить разделение auction-vs-order, которого требует домен. Расширение задокументировано как осознанное mock-отклонение и НЕ ДОЛЖНО протекать в production-типы `shared/api` или вышележащие FSD-слои.
